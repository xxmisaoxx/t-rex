# Migration from v2/v2.1 to v3

## v3.0 to v3.1 across coding agents
Canonical schema stays 3.0. Preserve the investigation directory, artifact revisions, evidence/maps/raw payloads and stable IDs; no JSON schema migration is required. Replace the installed skill tree with one v3.1 tree using the destination host's documented layout. Remove duplicate visible versions. Rebind relocated storage paths only after verifying the same artifact identity. Clear old context telemetry with reset-context, recover relevant state/NEXT, and verify required tools in the destination host. Sessions, token estimates, debugger attachments and background handles are not transferable by copying a chat session ID. See references/host-portability.md and the matching hosts adapter. The exporter stages files and does not modify existing host settings or instruction files.

## v2/v2.1 to canonical v3

1. Preserve original state/ledger/maps, raw evidence and artifact revisions in a backup. Install one skill version, preserving relative paths and the frontmatter name. Run old and new state in separate project directories until checks pass.
2. Resolve v2 duplicate ownership manually: compare CURRENT-STATE, INVESTIGATION, ledger and maps against original evidence. Conflicts become disputed/unresolved, not newest-timestamp wins. For v2.1 use its explicit canonical ownership.
3. Copy the v3 envelope. Retain Q/E/H IDs as strings where possible; create an explicit old→new ID table if formatting needs normalization. Keep supersession links. Never recycle an ID or invent support missing from old notes.
4. Populate immutable artifact records from verified files; record parent/change reason only when known. Hashes bind bytes; MVID/build-id/UUID/token/signature are useful scoped anchors, not substitutes for content identity. Choose active revision IDs. Lost old artifacts can remain metadata-only historical records, with limits; do not claim reverified bytes.
5. Move canonical ledger claims into the evidence array with exact proposition, class, confidence, validity, typed location, artifact IDs, dependencies, coverage/search boundary, recipe and limits. Set runtime=null for static claims. Runtime records retain input/environment/load/observation boundaries. UNKNOWN items become questions. Split mixed observation/interpretation into separate IDs and link them. Missing dependencies of a derivation must be recovered; otherwise preserve it as an unresolved legacy note rather than fabricate an observed base.
6. Convert question/hypothesis statuses and evidence links. Preserve completed-probe signature/outcome/novelty/retry condition; do-not-redo applies only to unchanged conditions. Replace free-text next_probe with question, active artifact IDs, capability, operation/parameters, scope, discriminator and fallback. Unrecoverable NEXT becomes null until a concrete probe is chosen.
7. Translate PE-MAP schema and other maps to revision-bound mappings, with E-ID links; do not duplicate claims/functions/patch histories in several canonical stores. Recipe output paths and map paths should remain reachable in the workspace. V3 map template is an example, not artifact detection.
8. Run `re_state.py validate STATE` then `--verify-files` for current artifacts. Fix dangling/cyclic dependencies, duplicate IDs, current claims on inactive revisions and obsolete NEXT. Keep original historical ledger archived as evidence, not a second live authority.
9. Generate CURRENT-STATE and optional ledger views; check checkpoint revision and execute the recovered NEXT. Recompute active-model telemetry after model switch. Test one real resume and one controlled artifact mutation before a long unattended run.

Migration is intentionally assisted/manual: arbitrary v2 prose cannot be transformed reliably by an automatic parser. There is no migration command claiming otherwise. New snapshots use schema_version=3.0 and checkpoint_revision with expected-revision writes. V2.1 remains usable independently if migration is deferred.
